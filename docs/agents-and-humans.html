Current Scope

OPE is a contract-first, agent-native forecasting package and standard. The current repository proves local, schema-bound forecast lifecycle mechanics before making hosted, broad-source, or quality claims.

What OPE does now

It validates contracts, generates checked fixtures, reads forecast cards and bundles, runs local forecast paths, resolves outcomes, scores forecasts, and exposes agent-readable envelopes.

What OPE does not claim

It is not a universal prediction oracle, hosted service runtime, unbounded crawler, trust authority, payment layer, or production live-data workflow.

Reference wedges

Run the normal checks

Claim boundary: Treat generated fixtures and one-off forward runs as mechanics evidence, not forecasting quality evidence. Track-record and calibration claims require comparable resolved sample sizes.

For Agents

Work from the repository rules, keep changes contract-first, preserve private data boundaries, and return machine-readable artifacts only when the checked implementation supports them.

Operating order

  1. Read AGENTS.md and .agents/rules.md.
  2. Use schemas and fixtures as the source of truth for engine behavior.
  3. Update generated fixtures with the matching --write command only when behavior intentionally changes.
  4. Run focused checks first, then the canonical checks before handoff or commit.

Safe local read examples

python3 scripts/ope.py read \
  --record-type forecast-card \
  --id forecast-502 \
  --question-id question-501

python3 scripts/ope.py agent-call \
  --operation private_setup_bundle \
  --private-setup-request-id privatesetuprequest-001
Live-source rule: Normal checks stay offline. Use opt-in live connector probes only when a developer explicitly asks for them and keep local captures under ignored workspaces.

Lifecycle

Every forecast-facing change should preserve the lifecycle below unless the relevant schemas, docs, fixtures, and checks change together.

1. Setup

Define a resolvable question, source policy, horizon, close time, resolution source, and output type.

2. Evidence

Gather or accept allowed evidence, normalize sources, record provenance, and block unsafe or unapproved inputs.

3. Forecast

Select baseline or benchmark-gated method, emit artifacts, and preserve forecast history before outcomes are known.

4. Recalculate

Append forecast updates only from pre-close evidence and keep post-outcome evidence out of forecast inputs.

5. Resolve

Resolve outcomes from declared sources, classify ambiguous or annulled outcomes, and keep unscorable cases explicit.

6. Score

Score against baselines, report sample-size limits, and keep calibration claims below threshold until evidence supports them.

Milestone Rule

Milestone commits should leave the docs in the same state as the implementation. A completed milestone is not done if humans or agents would be sent to stale instructions.

Required after each completed milestone: update human-facing docs, agent-facing docs, relevant specs, generated read surfaces, and the roadmap in the same milestone commit. If a milestone changes behavior, commands, boundaries, or next actions, update this page and the linked source documents before committing.

Minimum doc check

  • roadmap.md accurately marks the milestone status.
  • README.md and this HTML page reflect new user-visible behavior.
  • AGENTS.md and .agents/rules.md reflect new agent workflows or rules.
  • spec/*.md and schemas reflect contract or read-surface changes.

Commit expectation

Include docs, generated artifacts, checks, and decision-log entries in the same coherent milestone commit when they are part of the completed work.
